From proposal to supported release.

Documented local maintenance policy. This does not establish team adoption.

A change proposal needs a complete contract.

  1. Name the user task, affected component, languages, themes, states and existing consumers. Include the smallest reproducible example.
  2. Connect primitive values to semantic roles. Document keyboard order, focus, error behavior and long/mixed text before changing the implementation.
  3. Review the same task in Arabic and English, light and dark modes, narrow width and reduced motion. Keep test evidence and unresolved human checks separate.
  4. For a breaking API or token removal, document migration, retain the old name as a deprecated alias for a documented transition, and use a major version. Backward-compatible additions use a minor version; corrections use a patch.
  5. Update source, package, documentation and the design mapping together. A Figma change is verified separately; record drift when it remains.
  6. Build the packages, run source/package checks, inspect native interactions and the rendered states, then produce a dated release note and archive. Publish only when authorized.

The actual local release example

Package 1.5.0, recorded 2026-10-26: interaction color roles, component states, token resolution and package installation checks are listed in the quality record. The Figma companion retains the recorded 1.3 state. This discrepancy is explicit rather than treated as complete parity.

Acceptance and limitations

A passing software check establishes its named scope. Human screen-reader and language review, observed designer/developer use, cross-team adoption and efficiency comparisons remain outstanding. No deprecation is claimed to have occurred solely because this policy documents how to handle one.
